# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A container security scanner built for a backend home assignment. It scans container
images with Trivy on a schedule, stores CVE findings in PostgreSQL, and serves them
over a REST API.

**The assignment brief is preserved verbatim at `docs/ASSIGNMENT-REQUIREMENTS.md`.**
It is the contract this repo is judged against — read it before changing anything
user-visible, and re-run `scripts/verify_requirements.py` after.

The target is explicitly *production-grade at ~1000 images*, not
minimum-viable-for-ten. That premise is why several decisions below look heavier than
the brief strictly requires; each one is justified, and the justification matters as
much as the code.

Companion docs:
- `docs/ASSIGNMENT-REQUIREMENTS.md` — the original brief (never edit)
- `CONTEXT.md` — domain glossary (Image vs. Digest, Finding vs. CVE, Severity)
- `README.md` — the submission: setup, API examples, schema, and "Design decisions"

## Commands

### Run

```bash
docker compose up --build              # full stack; first run downloads the Trivy DB
docker compose up -d --scale worker=6  # concurrency is replica count
docker compose down -v                 # reset, including the Postgres volume
docker compose logs -f worker
```

Requires the Docker daemon. On this Windows machine `com.docker.service` has been
found stopped; starting it needs elevation (`net start com.docker.service` from an
admin shell).

### Verify — run all four before calling anything done

```bash
pytest                                  # 61 with Postgres; 42 pass/19 skip without
ruff check app tests scripts            # must be clean
python scripts/check_schema_drift.py    # models vs. the hand-written migration
python scripts/verify_requirements.py --wait 900 --with-db   # e2e vs. the brief
docker compose up --build               # must come up from cold with no local Trivy
```

`scripts/verify_requirements.py` is the important one: every check is labelled with
the brief requirement it proves (1.1, 2.3, 3.4 …). Exit code 0 means the assignment's
stated requirements are demonstrably met. `--with-db` adds SQL checks and actively
exercises the failure path by registering an unresolvable image.

### Narrower loops

```bash
pytest tests/test_parser.py -q                    # no DB needed
pytest -m postgres                                # DB-backed only
docker compose up -d postgres                     # unskips the 19 DB tests
ruff check app tests scripts --fix
uvicorn app.api.main:app --reload                 # API against an existing DB
python -m app.scheduler.scheduler
python -m app.scanner.worker                      # needs trivy on PATH
alembic upgrade head && python -m app.db.seed
```

### Inspecting a running system

```bash
docker compose exec postgres psql -U scanner -d scanner -c \
  "SELECT i.name||':'||i.tag AS image, j.status, j.priority, j.attempts, j.last_error
     FROM scan_job j JOIN image i ON i.id=j.image_id ORDER BY j.id;"

docker compose exec postgres psql -U scanner -d scanner -c \
  "SELECT i.name||':'||i.tag AS image, r.status, r.duration_ms, left(r.digest,20), r.error
     FROM scan_run r JOIN image i ON i.id=r.image_id ORDER BY r.id DESC LIMIT 20;"
```

## Architecture

Four processes over one PostgreSQL database.

- **`app/api/`** — FastAPI, read-only. **Contains no Trivy**, so the image stays thin
  and scan load never competes with request latency.
- **`app/scheduler/`** — advisory-locked singleton (`pg_try_advisory_lock`). Extra
  replicas idle rather than duplicate work, giving failover without leader election.
  Inserts due jobs; reaps expired leases.
- **`app/scanner/worker.py`** — synchronous, **one scan per process**. A wedged Trivy
  takes down one worker, not M in-flight scans. Scale = replica count.
- **`app/jobs/queue.py`** — the queue *is* Postgres (`FOR UPDATE SKIP LOCKED`).
- **`trivy-server`** (compose only) — owns the vulnerability database. Workers scan
  through it as thin clients and never open the database file themselves.

### Why these choices (the parts a reviewer will ask about)

**Postgres as the queue, not Redis/Celery.** A job's completion and the findings it
produced commit in *one transaction* — no at-least-once reconciliation, no
idempotency keys. The brief requires queryable scan status and failure history, so
the job table gets written either way; with a broker, job state lives under a TTL and
gets mirrored into Postgres anyway, creating two sources of truth. Throughput is not
the deciding factor either way: peak is ~1.1 jobs/sec at 1000 images.

**No Redis at all.** It lost its justification once the read cache was dropped. The
remaining use would be the rate limiter, and a counter row handles that at this rate.

**No read cache.** ~2M finding rows is unremarkable for indexed Postgres, and data
changes only every 15 minutes. What is avoided is the invalidation surface: a missed
invalidation means serving stale vulnerability data, the one wrong answer a security
tool must never give. `ETag`/`Last-Modified` off the newest scan completion give the
same benefit correct-by-construction.

**The registry is the binding constraint, not the worker pool.** Registries throttle
anonymous pulls well below 10-images-per-15-minutes sustained. Hence
`registry_budget`.

**Trivy client/server, not a shared cache directory.** This was changed after
measuring, and the measurement is the argument: the vuln DB is a single ~1.3 GB bbolt
file, and two workers sharing one cache took **116s** to scan an image that takes
**4s** through the server. Nothing errored — throughput just collapsed silently. Set
`SCANNER_TRIVY_SERVER_URL` and workers become thin clients. Do not go back to a
shared cache with more than one worker.

### Four invariants — breaking these corrupts results silently rather than raising

1. **A finding is "current" iff `finding.last_seen_run_id == image.current_scan_run_id`.**
   Every read path filters on this. Findings are never deleted — one that stops being
   reported just stops having `last_seen_run_id` advanced.

2. **A skipped run must NOT advance `image.current_scan_run_id`.** A skip means the
   previous run's findings are still correct; repointing would strand every one of
   them and make the image look clean. See `persist.record_skip`.

3. **Severity lives on `finding`, not `cve`.** Distros rate the same CVE differently.
   `cve.max_severity` is a derived rollup (`persist._recompute_cve_rollup`) over
   *current* findings only — so it must run **after** `current_scan_run_id` is
   updated.

4. **Scan skipping is a content invariant, not a timer**: digest + Trivy version +
   vuln DB version + flags hash all equal to the last successful run
   (`worker._is_unchanged`). Never replace this with elapsed-time logic — that is
   wrong in both directions: it skips scans a fresh vuln DB would light up, and runs
   scans that provably cannot differ.

## Conventions

**Layout.** One concern per package: `api/` (HTTP), `domain/` (models + vocabulary),
`scanner/` (Trivy + persistence), `scheduler/`, `jobs/` (queue), `ratelimit/`,
`registry/`, `db/`. Business rules do not live in route handlers.

**Database naming.** Singular snake_case table names (`scan_run`, not `scan_runs`).
Constraint and index prefixes are load-bearing — code references them by name in
`ON CONFLICT` clauses: `uq_` unique, `ix_` index, `ck_` check. Timestamps are
`timestamptz`, named `*_at`. Durations are `*_ms` or `*_seconds` — always unit-suffixed.

**Enums** are `VARCHAR + CHECK` (`native_enum=False`), never native PG enums, so
adding a value stays an ordinary constraint change.

**Config** is `SCANNER_`-prefixed env vars, all declared in `app/config.py`. Never
read `os.environ` elsewhere.

**Comments explain *why*, never *what*.** The codebase is dense with rationale for
non-obvious choices and has essentially no restating-the-code comments. Match that.

**Test naming states the behaviour**, not the function:
`test_defer_is_backpressure_not_failure`, not `test_defer`. Group by scenario in
classes (`TestClaim`, `TestSkipInvariant`). Tests that need Postgres carry
`pytestmark = pytest.mark.postgres` and skip cleanly when it is absent.

**Domain vocabulary comes from `CONTEXT.md`.** Use *Finding* for a CVE-in-a-package-in-
an-image, *Scan Run* for one attempt, *Digest* for content identity. Do not introduce
synonyms.

## Definition of done

A change is done when all of these hold:

1. `ruff check app tests scripts` is clean.
2. `pytest` passes; new logic has tests. Anything that can be *wrong* about Trivy
   output belongs in `parser.py` with fixtures, not in `trivy.py`.
3. If it touches models: `python scripts/check_schema_drift.py` exits 0. Migration
   `0001` is hand-written, so nothing else stops it drifting from the models.
4. If it touches scanning, persistence, or the API: `docker compose up --build` from
   cold, then `python scripts/verify_requirements.py --with-db` exits 0.
5. If it changes a decision: `README.md` "Design decisions" updated. That section is
   what the submission is defended with.
6. If it introduces or renames a domain term: `CONTEXT.md` updated.

## Things that will bite

- **`app/scanner/trivy.py` is deliberately thin (~120 lines, nearly half docstring)
  and has no test coverage** (the subprocess boundary is mocked). Do not grow it —
  every fallible decision belongs below it in `parser.py`, which is exhaustively
  fixture-tested.
- **The Trivy fixtures in `tests/fixtures/trivy/` are hand-authored** to the
  documented schema, not captured from a live run. Re-capture with
  `trivy image --format json nginx:1.19` before trusting them as a regression
  baseline.
- **`queue.defer` deliberately does not increment `attempts`.** Registry backpressure
  is not failure and must not burn a job's retry allowance.
- **`ScanJob.image` must stay `lazy="select"`.** A joined eager load puts it on the
  nullable side of an outer join, which Postgres refuses under `FOR UPDATE`.
- **One active job per image is enforced by a partial unique index**
  (`uq_scan_job_active`), not application logic. `queue.enqueue` returning `False` is
  normal, not an error.
- **Add queue operations as statement builders** (`build_enqueue_statement`,
  `build_promote_statement`) so the sync scheduler and async API share one definition
  rather than two that drift.
- **A worker's `trivy_cache_dir` must be writable and per-container**, never a shared
  volume. Trivy writes an artifact cache there (itself a bolt database). Mounting it
  read-only makes every scan a cold pull (measured: 75s vs 3s); sharing it between
  workers recreates the contention client mode exists to avoid. The server's cache is
  mounted separately at `trivy_db_dir`, read-only, purely to read `db/metadata.json`.
- **Never run more than one worker against a shared Trivy cache directory.** It does
  not error, it just serialises (~30x slower). Client mode via
  `SCANNER_TRIVY_SERVER_URL` is the supported configuration; standalone mode
  (`--skip-db-update` against a populated cache) is for a single worker only.
- **`trivy.db_version` reads `db/metadata.json` directly**, not `trivy --version`.
  In client mode the worker has no database, and in standalone mode a missing
  `--cache-dir` makes `trivy --version` silently report nothing — either way
  `trivy_db_version` would become a constant and defeat invariant 4.
- **Image names can contain slashes** (`bitnami/redis`). The route uses
  `{image_name:path}`; do not "simplify" it.
- **DB tests use a dedicated `<database>_test` database**, created on demand. They
  must not share one with a running stack: `queue.claim` takes the globally next due
  job, so they would claim the system's jobs and vice versa. Run them with
  `SCANNER_POSTGRES_HOST=localhost pytest`.
- **Queue time comparisons use `statement_timestamp()`, not `now()`.** `now()` is
  frozen at transaction start, so a job enqueued mid-transaction looks not-yet-due.
